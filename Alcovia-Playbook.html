PART I — KPI Framework & Metric Dictionary

0. Principles

  1. One metric, one definition, one owner. No re-deriving numbers in separate sheets.
  2. Every KPI answers a decision. If no action changes when it moves, it's vanity — drop it.
  3. Automate the collection, not the judgement. N8N moves data; humans interpret it.
  4. Inputs before outputs. Track leading indicators (show-up rate, feature reused) not just lagging ones (revenue, churn).
  5. Small-n honesty. At ~20 active students, report rates with the raw counts (5/11, not just 45%).

PART II — The Delivery OS

Goal: make every OKR (feature release, analytical upload, system change) land at its best — highest completion of its success metric, least cognitive load for teens and parents.

7. Why delivery fails (the five modes we kill)

Failure modeWhat it looks like at Alcovia
Shipping ≠ working"Realm is live" but only 13/20 students ever opened it
No owner of the outcomeSuccess judged by "it's released", not "the metric moved"
Cognitive load as polish6 tiles on Home; the teen doesn't know what to do next
No instrumentation at design timeCan't tell if it worked — argue from vibes
No kill/scale rulesWellness, Streak, Rankings, Goals sit at 0 habitual users

8. The system in one line

Every OKR is an artifact that walks through 8 gates. A gate only opens when its exit test passes. Done = the success metric moved, not code shipped. Weight by risk: a copy change takes the light path (gates 1, 2, 5); a new feature or analytical upload takes the full path.

INTAKE ─▶ 1 FRAME ─▶ 2 SUCCESS ─▶ 3 DESIGN ─▶ 4 BUILD ─▶ 5 VERIFY ─▶ 6 LAUNCH ─▶ 7 VERDICT
   │          │           │            │           │          │           │          │
 park if    reject     no metric    load fail   QA fail   regress     └─▶ SCALE / ITERATE / KILL
 no owner              → back 1     → back 3    → back 4  → rollback          │
                                                                                ▼ back to 1

9. Seven principles

  1. One OKR = one card = one outcome owner. No orphan work.
  2. The success metric is written before the build starts. Can't name it → not ready.
  3. Instrumentation-first. The event spec is part of the design.
  4. Least cognitive load is a gate. ≤3 taps to the core action; one primary CTA per screen; zero required decisions on first run.
  5. Two users, two lenses. Every feature passes a teen lens and a parent lens.
  6. Leading indicators before lagging. Track feature_reused, show-up, activation — not just revenue.
  7. Kill fast, scale fast. Explicit numbers decide; the lead doesn't.

10. The 8 gates

Each gate: goal → steps → artifact → exit test → owner.

Gate 0 — Intake

Goal: capture the OKR without committing. Steps: log on the OKR Delivery Card; tag type (Feature / Analytical upload / System / Growth). Exit test: it names a user (teen or parent) and a decision it serves. Else park. Owner: Lead.

Gate 1 — Frame (problem → hypothesis)

Goal: turn "build X" into "because Y, doing X will cause Z". Steps: one-sentence problem; hypothesis (Because ___, if we ___, then ___ changes); the one behaviour that must change. Exit test: a falsifiable hypothesis exists. Owner: Lead.

Gate 2 — Success metric (the contract)

Goal: make "done" objective. Steps: pick one primary metric (from Part I); set baseline → target → window; add guardrails; pre-commit kill/iterate/scale thresholds. Exit test: baseline measured, target numeric, window dated. Owner: Lead.

Analytical upload nuance: the metric isn't "uploaded" — it's "a decision was made using it."

Gate 3 — Design (least cognitive load)

Steps: 1-line user story per actor; count taps to core action (≤3); run Cognitive-Load Checklist + teen/parent lenses; write the Instrumentation Spec; define kill switch + feature flag. Exit test: both lenses pass; every metric has an event; a kill switch exists. Owner: Product/Design.

Gate 4 — Build

Steps: build to spec behind a flag; wire integrations (ClickUp / Smallest.ai / N8N / Razorpay); emit events; test the core path. Exit test: happy path works in staging; events land. Owner: Build/Automation.

Gate 5 — Verify

Steps: QA script; run 5 real teens (or 3 teens + 2 parents); measure completion, time-on-task, "did you know what to do?"; check Definition of Done. Exit test: ≥4/5 complete unaided and events verified. Owner: Lead (final) + both.

Gate 6 — Launch (staged)

Steps: 10% → 50% → 100% ramp; watch alert rules; daily read on primary + guardrails; flag ready. Exit test: guardrails green through ramp; no alert fires. Owner: Build/Automation (exec), Lead (call).

Gate 7 — Verdict

Steps: at T+window, read the dashboard against Gate 2; declare SCALE / ITERATE / KILL using pre-committed thresholds; write a 5-line Post-Launch Review. Exit test: a verdict is recorded and the next action scheduled. Owner: Lead.

Outcome loop: SCALE → raise target & widen rollout. ITERATE → back to Gate 1 with a new hypothesis (max 2, then KILL). KILL → switch off, capture learning, free the WIP slot.

12. Worked example — end to end

OKR: "Increase habitual Wellness use."

  1. 0 Intake: type = Feature; owner = Lead.
  2. 1 Frame: Because Wellness is opened but never repeated, if we convert it to a 30-second daily check-in tied to the streak, then habitual use will rise.
  3. 2 Success: Primary = Wellness habitual users 0 → 8 by T+14d. Guardrails = session length not down; Home completion not down. Kill if < 2 habitual.
  4. 3 Design: teen lens (1 tap from Home, 30s, no typing); parent lens (visible progress, no nag); events = wellness_opened / completed / reused_d3; kill switch = flag.
  5. 4 Build: daily check-in + streak tie-in only.
  6. 5 Verify: 5 teens; 5/5 complete <30s unaided; events land.
  7. 6 Launch: 10% → 100%; guardrails green.
  8. 7 Verdict (T+14): 6 habitual → ITERATE once (streak reward); still <8 → KILL and free the slot.

13. Process KPIs (are we getting better?)

  • OKR success rate (% reaching target) — aim ↑
  • Cycle time intake → launch
  • Rework % (items sent back a gate)
  • % features launched with events + kill switch — aim 100%
  • Rollback / incident rate
  • WIP vs limit adherence

PART III — Roles & Work Split

Mental model: the Lead owns the system that decides; the System Designer (full-stack) owns the system that runs. Same goals, two halves — "what should exist & why" vs "how it's built & kept alive."

14. System Designer · Full-stack — the work

WorkstreamConcrete work at Alcovia
1. Architecture & data contractsSource-of-truth schema (students, leads, calls, payments, app events); flow ClickUp/Smallest.ai/Meta/Razorpay/app → N8N → warehouse → dashboards; lock field names, types, timestamps; choose warehouse vs sheets vs app DB.
2. Integrations & automation (N8N)Funnel sync, call-outcome tagging, nurture, deadline alerts, payment reconcile, app-event → warehouse; alert rules, retries, error handling; own source health.
3. Product surface (full-stack)Student app features (Home, Realm, Focus, Wellness, Streak, Rankings, Goals, Syllabus, Planner) + dashboards (GTM Command Center, Student Progress) — front-end and the APIs/backends; role gate, theming, export, page speed.
4. InstrumentationEvent taxonomy; emit feature_opened / feature_reused; attribution; ensure events land, dedupe, backfill.
5. Reliability & observabilityMonitoring, error logs, data-freshness SLAs, feature flags, kill switches, secrets/PII hygiene.
6. Delivery / DevOpsRepos, CI, GitHub Pages deploys, staging vs prod, rollout mechanics (10 → 50 → 100%).

15. Lead — the work

WorkstreamConcrete work at Alcovia
1. Metric systemOwn the KPI Framework (definitions, targets, owners); write a Success Metric Sheet per OKR; enforce small-n honesty.
2. Delivery OSRun the 8 gates; chair Mon prioritise, Wed design review, Fri verdicts; enforce WIP limits and Definition of Done; make kill/scale calls.
3. Insight → decisionsRead dashboards, write RCAs, turn data into actions; run monthly business review and quarterly re-scope; own the blended-scorecard narrative.
4. PrioritisationIntake + rank OKRs (impact/effort); balance feature vs analytical vs system work.
5. Cognitive load & principlesReview every feature through teen + parent lenses; the ≤3-tap rule, one CTA. Non-negotiable gate.
6. Coaching & qualityLead the two teammates, unblock, review artifacts, own the final Verify gate.
7. Stakeholder & narrativeFounder comms; recommendation memos ("here's what the data says we should do").
8. GovernanceApprove data contracts and any metric change; guard the single source of truth.

17. What each role is NOT

  • Lead: doesn't write prod code, fix pipelines, or build dashboards.
  • System Designer: doesn't set targets, decide kill/scale, or own the data story.

18. Weekly rhythm

  • Lead: Mon prioritise → Wed design review → Fri verdicts → monthly/quarterly reviews → ad-hoc insight memos.
  • System Designer: daily build → Wed feasibility → Fri deploy → on-call for data freshness + alerts.

Rule of thumb: if it's a decision or a definition, it's the Lead's; if it's a build or a pipe, it's the System Designer's.
